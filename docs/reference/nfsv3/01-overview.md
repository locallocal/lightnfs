# 1. NFSv3 协议概述与体系结构

## 1.1 NFS 是什么

NFS（Network File System）由 Sun Microsystems 于 1984 年提出，目标是让客户端像访问本地文件系统一样透明地访问远程主机上的文件。NFSv3 由 RFC 1813（1995 年 6 月）定义，虽然是信息性（Informational）RFC，但长期以来是业界事实标准，Linux、FreeBSD、Solaris、各类 NAS 设备均有成熟实现，至今仍在生产环境广泛使用。

## 1.2 设计目标与核心理念

NFSv3 继承了 NFSv2 的核心设计哲学，并针对 v2 的短板做了修补：

1. **无状态服务器（stateless server）**：服务器不为客户端维护打开文件表、会话等状态。每个请求都自包含（self-contained），携带完成操作所需的全部信息（文件句柄、偏移、长度等）。服务器崩溃重启后客户端无感知地重试即可恢复，无需复杂的状态重建协议。
   - 例外：文件锁本质上是有状态的，因此被剥离到独立的 NLM/NSM 协议中（见 [06-nlm-nsm.md](06-nlm-nsm.md)）。
2. **操作系统无关**：通过 XDR 统一数据表示，通过通用的文件模型（层次目录 + 常规文件 + 符号链接 + 设备文件）屏蔽 OS 差异，但整体模型明显偏向 POSIX/UNIX 语义。
3. **传输无关**：构建在 ONC RPC 之上，可以跑在 UDP 或 TCP 上（v3 时代 TCP 开始成为主流）。
4. **可恢复性优先于强一致性**：NFSv3 不提供跨客户端的强缓存一致性，只提供"close-to-open"一致性惯例和弱缓存一致性（WCC）辅助数据。

## 1.3 相对 NFSv2 的主要改进

| 方面 | NFSv2 (RFC 1094) | NFSv3 (RFC 1813) |
|------|------------------|------------------|
| 文件大小/偏移 | 32 位（最大 2GB/4GB） | **64 位** |
| 文件句柄 | 固定 32 字节 | **可变长，最大 64 字节** |
| 写语义 | 每次 WRITE 必须同步落盘 | **异步写（UNSTABLE）+ COMMIT**，大幅提升写吞吐 |
| 单次读写上限 | 8KB（惯例） | 由服务器 FSINFO 通告，**无协议上限** |
| 权限检查 | 客户端自行猜测 | 新增 **ACCESS** 过程，由服务器裁决（正确处理 root squash、ACL 等） |
| 目录读取 | READDIR 只返回名字，需逐项 LOOKUP/GETATTR | 新增 **READDIRPLUS**，一次返回名字 + 属性 + 句柄 |
| 缓存一致性辅助 | 无 | 大多数修改操作返回 **WCC 数据**（操作前后属性） |
| 创建语义 | 无排它创建保证 | CREATE 支持 **EXCLUSIVE** 模式（借助 8 字节 verifier） |
| 设备文件 | 塞在 sattr 里的 hack | 独立的 **MKNOD** 过程 |
| 属性返回 | 部分操作返回 | 几乎**每个操作都随带 post-op 属性**，减少 GETATTR 往返 |

## 1.4 与 NFSv4 的对比（为什么很多场景仍用 v3）

NFSv4（RFC 7530/8881）走向了完全不同的设计：有状态、复合操作（COMPOUND）、内建锁与委托（delegation）、强制 RPCSEC_GSS 安全、单一 well-known 端口 2049、去掉 MOUNT/NLM 辅助协议。v3 的优势在于：

- 实现简单，服务器几乎无状态，故障恢复模型极其简单；
- 协议成熟稳定，交互轮次直观易调试；
- 在受信内网、低延迟场景性能不输 v4。

对 lightnfs 这类轻量实现，v3 是合理的起点。

## 1.5 协议栈全景

NFSv3 不是一个协议，而是一族协议的组合：

```
┌───────────────────────────────────────────────────────┐
│  应用（VFS 层 / NFS 客户端内核模块）                    │
├──────────┬──────────┬──────────┬──────────┬────────────┤
│ NFS v3   │ MOUNT v3 │ NLM v4   │ NSM v1   │ rpcbind v2+│
│ 100003   │ 100005   │ 100021   │ 100024   │ 100000     │
│ 文件操作 │ 取根句柄 │ 文件锁   │ 崩溃通知 │ 端口发现   │
├──────────┴──────────┴──────────┴──────────┴────────────┤
│  ONC RPC（RFC 5531）：消息帧、事务 ID、认证             │
├─────────────────────────────────────────────────────────┤
│  XDR（RFC 4506）：数据序列化                             │
├─────────────────────────────────────────────────────────┤
│  TCP（记录标记帧）/ UDP（一报文一消息）                  │
└─────────────────────────────────────────────────────────┘
```

各组件端口：只有 rpcbind 的端口是固定的（111）。NFS 服务惯例上监听 2049，MOUNT、NLM、NSM 传统上使用动态端口并注册到 rpcbind（实践中常固定下来以便穿透防火墙）。

## 1.6 一次典型挂载与访问的完整时序

以 `mount -t nfs server:/export /mnt` 后 `cat /mnt/dir/file` 为例：

```
客户端                                      服务器
  │ 1. rpcbind GETPORT(100005,3,tcp) ────────▶ :111
  │ ◀──────── MOUNT 端口（如 20048）
  │ 2. MOUNT3 MNT("/export") ────────────────▶ :20048
  │ ◀──────── fhandle3（根句柄）+ auth flavors
  │ 3. rpcbind GETPORT(100003,3,tcp) ────────▶ :111
  │ ◀──────── NFS 端口（2049）
  │ 4. NFS3 FSINFO(根句柄) ──────────────────▶ :2049
  │ ◀──────── rtmax/wtmax/dtpref/properties...
  │ 5. NFS3 GETATTR / PATHCONF(根句柄)
  │    （挂载完成）
  │ 6. NFS3 LOOKUP(根句柄, "dir") ───────────▶
  │ ◀──────── dir 的句柄 + 属性
  │ 7. NFS3 ACCESS(dir句柄, READ|LOOKUP)
  │ 8. NFS3 LOOKUP(dir句柄, "file")
  │ 9. NFS3 READ(file句柄, offset=0, count=...)
  │ ◀──────── 数据 + eof 标志 + post-op 属性
```

要点：

- **文件句柄是贯穿一切的钥匙**。客户端从 MOUNT 拿到根句柄后，此后所有导航都靠 LOOKUP 一级一级换取子句柄；客户端把句柄当不透明字节串缓存，跨重启仍应有效（句柄持久性是服务器的责任）。
- **NFSv3 没有 open/close**。读写直接凭句柄 + 偏移进行，这正是无状态设计的体现。
- **路径解析在客户端**。服务器一次只处理一个分量（LOOKUP 单分量），不接受整条路径（避免了服务器端对客户端命名空间语法的依赖，也简化了符号链接处理——READLINK 把链接内容交回客户端自行解析）。

## 1.7 NFSv3 的文件模型

- 文件系统是**目录树**；每个文件系统对象由**文件句柄**唯一标识。
- 支持 7 种对象类型（`ftype3`）：常规文件、目录、块设备、字符设备、符号链接、socket、FIFO。
- 硬链接：同一句柄可出现在多个目录项下；`fileid`（类似 inode 号）在文件系统内唯一。
- 一个 NFS 服务器可导出多个文件系统；**LOOKUP 不跨越文件系统边界**（客户端需分别挂载，或由服务器实现决定是否允许跨越）。
- 属性模型基本对应 POSIX `struct stat`，外加 `used`（实占字节）、`fsid`、`rdev` 等。

## 1.8 无状态带来的三个关键工程问题

这三个问题贯穿整个协议设计，后续文档反复出现：

1. **幂等性与重复请求**：UDP 上重传、TCP 重连后重发都会造成请求重复执行。READ/GETATTR 天然幂等；REMOVE/CREATE/RENAME 等不幂等（重放 REMOVE 会返回 NOENT）。业界标准解法是服务器维护**重复请求缓存（DRC, Duplicate Request Cache）**，按 (xid, 客户端地址, 过程号) 记住最近应答直接重放。协议本身不规定 DRC，但不做就会出现虚假错误。
2. **崩溃恢复与异步写**：v3 的 UNSTABLE 写 + COMMIT 机制把"数据何时落盘"的控制权交给客户端，用 **write verifier**（8 字节，服务器每次重启改变）让客户端检测到"服务器在 COMMIT 前重启过"，从而重发未提交数据。
3. **弱缓存一致性**：服务器在修改类操作中返回操作前属性（pre-op：size/mtime/ctime）+ 操作后属性（post-op），客户端据此判断"这次修改之间是否有别人动过文件"，决定是否作废本地缓存。

## 1.9 安全模型（简述，详见各分册）

- RPC 层认证：实践中绝大多数 v3 部署使用 **AUTH_SYS**（明文传 uid/gid/gids，完全基于信任），可选 RPCSEC_GSS（Kerberos）。
- 授权：服务器按请求中的凭证对底层文件系统做权限检查；ACCESS 过程让客户端询问真实权限。
- 导出控制在 MOUNT 层（按客户端 IP/网段允许导出、root squash 等），但注意：**NFS 服务本身通常不再校验句柄来源**，拿到句柄即可访问——句柄不可猜测性和导出检查是服务器实现必须自己补强的（见 [09-implementation-notes.md](09-implementation-notes.md)）。
